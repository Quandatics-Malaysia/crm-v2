title: app/ — App Router

`apps/web/app/` is a standard Next.js 16 App Router tree with one added
convention: **every route module is self-contained** — its page, its client
components, and its server actions live together in one directory, not
spread across `pages/`, `api/`, and a separate actions folder.

## Top-level layout

```
app/
  (app)/            route group — the authenticated CRM shell
    _shared/        cross-module helpers used by more than one route module
    accounts/  approvals/  audit/  billing/  dashboard/  forecast/
    funnel/  intercompany/  leads/  opportunities/  payment-milestones/
    persons/  products/  projects/  purchasing/  quotations/
    sales-orders/  settings/  tax-settings/  team/
    error.tsx  layout.tsx  loading.tsx  not-found.tsx
  (auth)/           route group — sign-in, outside the app shell
  api/               4 route handlers (see below)
  documentation/     the in-app docs viewer (gated by the `documentation` module)
  layout.tsx  page.tsx  global-error.tsx  globals.css  favicon.ico
```

The `(app)` and `(auth)` segments are Next.js **route groups** — the
parentheses mean the segment name doesn't appear in the URL. `(app)/layout.tsx`
is where the authenticated shell (sidebar, header, module on/off map) is
assembled once for every route under it.

Not every item in the `(app)` list is an optional module: `accounts`,
`leads`, `persons`, `opportunities`, `funnel`, `quotations`, `products`,
`dashboard`, `payment-milestones`, `team`, `settings`, `tax-settings` are
**core** and always present. `projects`, `sales-orders`, `billing`,
`purchasing`, `forecast`, `audit`, `intercompany` are gated behind a flag in
`modules.config.ts` — see [Modules Guide](/modules/overview) and
[Adding a module](/codebase/adding-a-module).

## The per-module route pattern

Every route module under `(app)/` follows the same three-file split. Reading
`app/(app)/projects/` end to end:

```
projects/
  page.tsx                     Server Component — the list page
  loading.tsx                  Suspense fallback for page.tsx
  actions.ts                   "use server" — every query + mutation for this module
  projects-table.tsx           "use client" — renders the list (DataTable)
  project-create-form.tsx      "use client" — the create dialog/form
  new/page.tsx                 a full-page create route (alternate entry point)
  [id]/
    page.tsx                   Server Component — the detail page
    loading.tsx
    project-detail-body.tsx    "use client" — detail view
    project-edit-button.tsx
    milestones-panel.tsx
    billing-panel.tsx
```

### `page.tsx` — server-rendered, thin

`app/(app)/projects/page.tsx` is representative: it is `async`, calls
`requireModule("projects")` as the very first statement (the route guard —
see [lib.mdx](/codebase/lib)), then fetches everything it needs by directly
calling functions from the sibling `actions.ts` (not `fetch`):

```ts
export default async function ProjectsPage({ searchParams }: { ... }) {
  requireModule("projects")
  const [rows, ctx, sp] = await Promise.all([
    listProjects(),
    requireContext(),
    searchParams,
  ])
  // conditionally build a <ProjectCreateForm> if ctx.can(PERMISSIONS.PROJECT_CREATE)
  return (
    <>
      <SiteHeader title="Projects" />
      <PageBody>
        <ProjectsTable data={rows} toolbar={newButton} />
      </PageBody>
    </>
  )
}
```

Permission checks that affect *what renders* (e.g. whether the "New project"
button appears at all) are done here with `ctx.can(PERMISSIONS.X)`, in
addition to the enforcement inside the action itself — the action is always
authoritative, the page-level check is just UX (no dead-end button that would
be denied on click).

### `actions.ts` — `"use server"`, the module's real API

`app/(app)/projects/actions.ts` is a single ~1100-line file exporting every
read and write for the module: `listProjects`, `getProject`, `createProject`,
`updateProject`, `deleteProject`, plus the payment-milestone CRUD that hangs
off a project. Every exported function follows one of two shapes:

**Reads** call `withModule`/`withTenant` directly and return data (they throw
on failure — they run inside a Server Component, which has `error.tsx`):

```ts
export async function listProjects(): Promise<ProjectListItem[]> {
  return withModule("projects", PERMISSIONS.PROJECT_VIEW, async (tx, ctx) => {
    const visible = await visibleMemberIds(tx, ctx)
    return tx.select({ ... }).from(projects)
      .where(and(isNull(projects.deletedAt), ownerScope(projects.ownerMemberId, visible)))
      .orderBy(desc(projects.createdAt))
      .limit(1000)
  })
}
```

**Mutations** wrap the whole body in `runAction(...)` so failures come back
as `ActionResult` instead of a thrown Flight-digest error, call
`revalidatePath(...)` after the write commits, and route-scope their own
business rules (numbering via `nextProjectCode`, milestone auto-seeding via
`splitMilestones`, activity logging via `logActivity`, audit via
`writeAudit`):

```ts
export async function createProject(
  input: ProjectCreateInput
): Promise<ActionResult<{ id: string; projectCode: string }>> {
  return runAction(async () => {
    const created = await withModule("projects", PERMISSIONS.PROJECT_CREATE, async (tx, ctx) => {
      // validate account, mint projectCode via nextProjectCode(tx, ctx, ...),
      // insert, logActivity, writeAudit, seed milestones from the tenant template
      return row
    })
    revalidatePath("/projects")
    return created
  })
}
```

Row-level ownership (not just the coarse permission) is checked inline where
it matters — `updateProject`/`deleteProject` load the row `for("update")`
(row lock), then require `canManageAllRecords(ctx) ||
ownsOrManages(visible, before.ownerMemberId)` before proceeding. See
[lib.mdx](/codebase/lib) for `access-scope.ts`.

### Client components — thin, typed off the action's own types

`projects-table.tsx` imports its row type straight from `./actions`
(`import type { ProjectListItem } from "./actions"`) rather than redeclaring
it — the action file is the source of truth for the shape crossing the
server/client boundary. It composes the shared `DataTable` from
`components/data-table.tsx` with column defs local to the file.

### A second example: `quotations/`

`app/(app)/quotations/` follows the identical shape with one addition worth
noting — `[id]/preview/page.tsx`, a print-oriented view with its own
`print-button.tsx`. This is the pattern for "a route needs a substantially
different render of the same entity": a sibling route under `[id]/`, not a
query param on the main detail page.

## `app/api/` — the 4 route handlers

Almost none of the app's read/write traffic goes through HTTP JSON — it goes
through Server Actions (above). `app/api/` holds exactly the handlers that
*must* be real HTTP endpoints:

| Route | File | Why it's a route handler, not a Server Action |
|---|---|---|
| `GET /api/health` | `app/api/health/route.ts` | Liveness probe hit by Docker/orchestration — needs a plain HTTP response. |
| `ALL /api/auth/[...all]` | `app/api/auth/[...all]/route.ts` | Better Auth's own catch-all handler (`toNextJsHandler(auth.handler)`) — sign-in, OAuth callbacks, session endpoints. |
| `GET /api/files/[id]` | `app/api/files/[id]/route.ts` | Streams raw file bytes (`Content-Type`/`Content-Disposition`) — Server Actions can't return a binary stream response. |
| `GET /api/tenant-logo` | `app/api/tenant-logo/route.ts` | Same reasoning — binary image response. |

Full request/response contracts (auth, params, status codes) for each are
documented in [API Reference → Route handlers](/api-reference#route-handlers).
Default to a Server Action for anything new; only reach for a route handler
when you need a non-JSON response, a webhook target, or something outside
Next's request lifecycle.

## Adding a new route/page

For a route inside an **existing** module (e.g. a new tab on the project
detail page): add a file under `[id]/`, add any new query/mutation to the
module's `actions.ts` following the shapes above, and if it's a module gated
by `modules.config.ts`, keep the `requireModule("x")` guard.

For a **brand-new top-level route module**, follow this shape:

1. Create `app/(app)/<name>/page.tsx`, `loading.tsx`, `actions.ts`, and the
   client components it needs, mirroring `projects/` above.
2. `page.tsx` starts with `requireModule("<id>")` if the route belongs to an
   optional plugin (skip this line for a core route).
3. Every exported action in `actions.ts` goes through `withTenant(...)` (core)
   or `withModule("<id>", ...)` (plugin) — never a raw `db` query.
4. Add the nav entry in `components/app-sidebar.tsx` (and
   `components/command-palette.tsx` for the command palette), tagged with
   `module: "<id>"` if applicable.
5. If the route needs a new permission, add it to `PERMISSIONS` in
   `lib/permissions.ts` and to the relevant `ROLE_TEMPLATES`.

See [Adding a module](/codebase/adding-a-module) for the full worked
walkthrough (Projects and Finance), including the schema/migration/seed steps
that go alongside the route.
