title: lib/ — the shared kernel
---

`apps/web/lib/` is ~30 files. Most are small, focused, and imported from many
route modules; a handful are the load-bearing core that every mutation in the
app passes through. This page groups them by purpose and documents the ones
worth knowing by name.

## Auth & request context

**`auth.ts`** configures [Better Auth](https://better-auth.com): the
`organization()` plugin as the tenancy backbone, `drizzleAdapter` over the
Drizzle schema, Microsoft Entra ID via `genericOAuth`, and several hooks —
`consumePendingInvites` / `autoJoinByDomain` on user creation,
`passwordLoginAllowed` enforcing the per-tenant `allow_password_login` flag
in `hooks.before`, and a `session.create.before` hook that stamps
`lastLoginAt`, resolves the active organization deterministically, and writes
a login audit row. `nextCookies()` must stay last in the `plugins` array.

**`server-context.ts`** resolves the authenticated request into a
`ServerContext`:

```ts
export type ServerContext = {
  userId: string; userName: string; userEmail: string
  isSuperadmin: boolean
  tenantId: string          // active organization id; "" if no membership
  memberId: string | null
  tierLevel: number
  roleName: string | null
  status: "active" | "invited" | "disabled"
  tenantSuspended: boolean
  permissions: Set<string>
  can: (key: PermissionKey | string) => boolean
}
```

`getServerContext()` reads the Better Auth session, resolves the member row
for the active org (falling back to the user's oldest membership — a stable
choice for multi-org users), unions the permissions of **every** role the
member holds via `member_roles` (falling back to the legacy single
`membership_profiles.role_id`), and zeroes out `permissions` entirely if the
member isn't `active` or the tenant is `suspended`. `requireContext()` is the
throwing variant used by server actions: it raises `UNAUTHENTICATED`,
`NO_ACTIVE_TENANT`, a suspension message, or an inactive-membership message.
`assertCan(ctx, key)` throws `` FORBIDDEN: missing <key> `` — the exact
string `runAction` pattern-matches on (see below).

## Action wrappers — `actions.ts` + `action-result.ts`

**`actions.ts`** exports the two functions nearly every server action in the
app is built from:

```ts
async function withTenant<T>(
  permission: PermissionKey,
  fn: (tx: Tx, ctx: ServerContext) => Promise<T>
): Promise<T>

async function withModule<T>(
  moduleId: ModuleId,
  permission: PermissionKey,
  fn: (tx: Tx, ctx: ServerContext) => Promise<T>
): Promise<T>
```

`withTenant` is `requireContext()` → `assertCan(ctx, permission)` →
`runInTenant(ctx.tenantId, (tx) => fn(tx, ctx))` — authenticate, authorize,
then open a transaction with the RLS GUC (`app.current_tenant`) set for its
duration. `withModule` is `assertModuleEnabled(moduleId)` followed by exactly
that — use it for every action belonging to an optional plugin (`projects`,
`salesOrders`, `finance`, `forecast`) so a disabled plugin's actions throw
before ever touching the database, as defense in depth behind the hidden nav
and the route redirect.

**`action-result.ts`** defines the return type mutations use instead of
letting exceptions cross the Server Action boundary:

```ts
export type ActionResult<T = undefined> =
  | { ok: true; data: T }
  | { ok: false; error: string; contact?: DenialContact }
```

The reason is concrete: in production, React's Flight encoder strips a
thrown error down to an opaque digest, so an expected failure (permission
denied, a business-rule violation) has to be modeled as a return value, not a
throw. `runAction(fn)` runs `fn`, catches any `Error`, logs it server-side,
and humanizes a `FORBIDDEN:` message via `humanizeDenial` (never leaking a
raw permission key to the client) — additionally resolving a `contact`
(the user's manager, or an Owner/Admin) via `resolveDenialContact` so the
client can tell the user *who* to ask instead of dead-ending. Read-only
actions that run inside Server Components skip `runAction` and just throw —
they're covered by `error.tsx`.

## The module system

**`modules.ts`** is the plugin registry: `ModuleId` (derived from
`MODULE_CONFIG`'s keys in the root `modules.config.ts`), the `MODULES`
metadata + dependency graph, and the three gate functions
(`isModuleEnabled`, `assertModuleEnabled`, `validateModuleConfig`).
**`module-guard.ts`** is a deliberately tiny, separate `server-only` file
holding just `requireModule(id)` — an RSC/layout guard that
`redirect("/dashboard")`s when a plugin is off — kept apart from
`lib/actions.ts` so a page doesn't transitively pull in the whole `db` graph
just to gate itself. Full treatment: [Modules Guide](/extensibility/overview).

## Permissions

**`permissions.ts`** is the single source of truth for the permission
catalog and role templates, seeded per-tenant into `permissions`, `roles`,
and `role_permissions`. `PERMISSIONS` is a flat `resource.action` string
map (`LEAD_VIEW: "lead.view"`, `PROJECT_CREATE: "project.create"`, …).
`ALL_GROUPS` organizes them for the role-matrix UI, each group optionally
tagged `module?: ModuleId`; `PERMISSION_GROUPS` filters that list by
`isModuleEnabled`, while `PERMISSION_LABELS` is built from the **unfiltered**
list so a denial for a disabled module's permission still resolves a
friendly label. `ROLE_TEMPLATES` seeds six tiers (Owner 100, Admin 90,
Manager 60, Senior Rep 40, Rep 20, Viewer 10) — Owner/Admin hold `"*"`.
`humanizeDenial(message)` turns a raw `FORBIDDEN: missing <key>` thrown
message into `"You don't have permission to do this (<label>)."`.

## Tenant/RLS context & record-level access

**`access-scope.ts`** implements *record-level* access on top of tenant
isolation: `visibleMemberIds(tx, ctx)` returns the set of member ids whose
records `ctx` may see — `null` for "no filter" (holder of
`records.view_all` or superadmin), `[]` for "sees nothing of their own", or
the transitive closure of `ctx.memberId` plus everyone reporting up through
`membershipProfiles.managerMemberId`. `ownerScope(column, visible)` turns
that into a SQL predicate (`undefined` / `inArray` / a fail-closed `false`).
`attachableOwner(tx, type, id)` resolves the owning member of whatever record
an attachment hangs off (account, lead, opportunity, project, person,
quotation, sales order, …), and `canAccessAttachable` combines both
capability (permission) and ownership checks for the attachment routes/
actions. Finance documents are the one type with no owner column — access
there is purely `isModuleEnabled("finance")` plus the `finance.view`/
`finance.manage` capability.

## Formatting & small pure helpers

`format.ts` (money/number formatting), `dates.ts` (`toDateString` and
friends), `status-meta.ts`, `funnel-stages.ts`, `stage-gate.ts`,
`quote-number.ts` (the `Q{yy}-...` reference format, `QUOTE_PAD_WIDTH`),
`opportunity-code.ts`, `milestone-split.ts` (`splitMilestones` — pure,
unit-tested in `tests/milestone-split.test.ts`), `finance-kinds.ts` (the
finance-doc-chain config table), `interco-share.ts`, `so-milestones.ts`,
`reminders.ts`, `validation-quotation.ts`, `lookups.ts`,
`tenant-defaults.ts`, `utils.ts` (the shadcn `cn()` helper),
`show-action-error.ts`, `permission-denial.ts`, `bootstrap.ts`. These are the
things you reach for when a route needs a small, reusable, mostly-pure
calculation or formatter that doesn't warrant a `server/services/` module
(no `Tx`/`ServerContext` plumbing) and isn't specific to one route.

## Env & infrastructure

**`env.ts`** centralizes `process.env` access and is deliberately
non-throwing at import time (`next build` and `drizzle-kit` must not crash
on a missing secret) — it exposes `env.DATABASE_URL` (the RLS-enforced
`crm_app` connection), `env.DATABASE_ADMIN_URL` (the privileged
migration/seed connection), auth secrets, Microsoft Entra config, and the
storage driver selection, plus derived `isProd` / `microsoftConfigured`
booleans.

**`storage.ts`** defines the `StorageService` interface (`put`/`get`/
`delete`) and the only current implementation, `LocalStorage` — a
filesystem driver rooted at `env.STORAGE_LOCAL_DIR`, with a `resolveSafe`
path-traversal guard. An S3/MinIO driver is a documented future drop-in
behind the same interface; there's no abstraction to add, just a second
class to write and wire up via `env.STORAGE_DRIVER`.

## Conventions for adding a lib helper

- **`server-only` at the top** of anything that touches auth, the DB, or a
  secret — `lib/actions.ts`, `lib/auth.ts`, `lib/module-guard.ts`,
  `lib/storage.ts` all start with `import "server-only"`. Files meant to be
  safely importable from client code (`modules.ts`, `permissions.ts`'s pure
  parts) deliberately omit it.
- **Keep the module registry pure.** `modules.ts` and the root
  `modules.config.ts` have *no* imports beyond each other and are read from
  client components, server components, actions, framework-free services,
  and seed scripts alike — don't add a `db` or `next/*` import to either.
- **A helper that needs a `Tx`/`ServerContext` and encodes a business rule**
  (not just formatting/parsing) belongs in `server/services/`, not `lib/` —
  see [server/services](/codebase/server-services).
- **A helper specific to one route module's data shape** belongs in that
  module's `actions.ts`, not `lib/` — `lib/` is for helpers more than one
  route module needs.
