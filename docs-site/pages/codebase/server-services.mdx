---
title: server/services/ — business rules
---

`apps/web/server/services/` holds the app's business rules — the logic that
would still make sense running in a worker, a script, or a test, completely
outside an HTTP request. That's not an aspiration; it's an enforced
invariant checked in review (see [Modules Guide → invariant
5](/extensibility/adding-a-module#the-five-invariants)):

> **Business rules stay framework-free.** Code under `server/services/*`
> must not import `next/*`. Data access from a service goes through a `Tx`
> handed to it by the caller — the caller (a server action) is the one that
> opened it via `withTenant`/`withModule`.

`apps/web/server/` also has two files outside `services/`: `audit.ts`
(`writeAudit`, `writeAuthAudit`) and `changes/` (`recordChanges` — diffed
change-history entries), following the same framework-free convention.

## What's in there

`activity.ts` (`logActivity`), `conversion.ts` (lead→account/person
conversion), `finance.ts` (`maybeCompleteProject` — auto-complete a project
once every milestone is paid), `intercompany.ts` (cross-tenant deal
mirroring), `numbering.ts` (quote/SO/project code minting), `opportunity-
container.ts`, `owner-cascade.ts`, `quotation-math.ts` (`computeQuotation`),
`quote-sync.ts`, `stage.ts` (the funnel stage/approval state machine),
`tenant-currency.ts`, `tenant-seed.ts`, `value.ts` (opportunity net-value
derivation).

## The convention, read from the code

**No `next/*` imports; `server-only` instead, when it needs one.**
`server/services/numbering.ts`, `value.ts`, and `finance.ts` all start with
`import "server-only"` — this blocks the file from ever being pulled into a
client bundle, but it is *not* a Next.js API import, so the file still runs
in any Node context (a script, a test, a worker) that isn't a browser.

**Every function takes a `Tx` (and usually a `ServerContext`) as a
parameter — it never opens its own transaction.** The caller (always a
Server Action via `withTenant`/`withModule`) owns the transaction and its RLS
scope; the service just uses it:

```ts
// server/services/numbering.ts
export async function nextProjectCode(
  tx: Tx,
  ctx: ServerContext,
  { accountCode, projectNatureCode, year }: { ... }
): Promise<string> {
  const [counter] = await tx
    .insert(projectCounters)
    .values({ tenantId: ctx.tenantId, year, nextNumber: 2 })
    .onConflictDoUpdate({
      target: [projectCounters.tenantId, projectCounters.year],
      set: { nextNumber: sql`${projectCounters.nextNumber} + 1` },
    })
    .returning({ next: projectCounters.nextNumber })
  // ...format {YYYY}-{ENTITY}-{ACCOUNTCODE}-{PROJECTNATURE}-{NNN}
}
```

**Pure computation stays pure — no `Tx` at all when none is needed.**
`server/services/quotation-math.ts`'s `computeQuotation` takes plain data in,
returns plain data out, and asserts its own reconciliation invariant
(`subtotal + taxTotal − discountTotal === total`, both in tax-inclusive and
tax-exclusive modes) before returning. It has no imports beyond its own
types — this is why it's directly unit-tested in `tests/quotation-math.test.ts`
with no DB or auth fixture required.

**Cross-module logic uses a guarded dynamic import, never a static one.**
`server/services/value.ts`'s `syncOpportunityAmount` is core (funnels are
core), but it needs to notify the `finance` plugin's intercompany mirror
when a quote-driven value changes:

```ts
// every quote-driven value change pipelines through here, so this is the one
// choke point that keeps the partner-facing intercompany mirror aligned.
if (isModuleEnabled("finance")) {
  const { syncIntercompanyMirror } = await import("./intercompany")
  await syncIntercompanyMirror(tx, funnelId)
}
```

If `finance` were statically imported at the top of `value.ts`, core would
carry a build-time dependency on the finance plugin even with the flag off —
exactly the coupling invariant 3 in [Modules Guide →
Contributing](/extensibility/adding-a-module) forbids. `server/services/stage.ts` has
the same pattern for its own call into `intercompany.ts`.

## How to add a service

1. Create `server/services/<name>.ts`. Add `import "server-only"` if the
   file touches the DB, secrets, or anything not safe for a client bundle;
   omit it for a genuinely pure module like `quotation-math.ts`.
2. Every exported function that reads/writes data takes `tx: Tx` as its
   first parameter (import the type from `@/db`), and `ctx: ServerContext`
   when it needs tenant/permission/actor context. Never call
   `runInTenant`/`withTenant` from inside a service — that's the caller's
   job.
3. If the logic needs to reach into an optional plugin's code, use the
   `isModuleEnabled(...)` + `await import(...)` guard shown above — never a
   static `import` at the top of the file pointing at a module's `app/(app)/
   <module>/actions.ts` or another plugin-only service.
4. Call the service from the owning route module's `actions.ts`, inside the
   `withTenant`/`withModule` callback, passing the `tx`/`ctx` it received.
5. If the function is pure (no `Tx`), add a `tests/<name>.test.ts` — this is
   the class of code the test suite actually covers; see
   [components-and-tests.mdx](/codebase/components-and-tests).

## What does *not* belong here

- Anything reading `headers()`, `cookies()`, calling `redirect()`, or
  otherwise touching `next/*` — that's `lib/` or the route's own
  `actions.ts`.
- Anything that opens its own transaction or calls `getServerContext()`
  directly — services are handed context, they don't resolve it.
- UI logic, formatting for display, or anything route-shape-specific — those
  belong in the route module or in `lib/format.ts` and friends.
