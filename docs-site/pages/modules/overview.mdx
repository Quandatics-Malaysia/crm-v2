# The module (plugin) system

Everything beyond the **core CRM** — leads, accounts, contacts/persons,
opportunities, the funnel with stage-gated approvals, quotations, tax,
products, the pipeline dashboard, and RBAC/Team — is an **optional plugin**.
Each plugin is switched on or off for the **whole deployment** by a single
boolean in `apps/web/modules.config.ts`. There is no per-tenant flag and no
runtime toggle — flipping a value requires a rebuild and redeploy.

Guiding principle: **disable, don't delete.** Turning a plugin off hides its
nav entries, redirects its routes, refuses its server actions, and hides its
permission-matrix group. Its database tables, migrations, RLS policies, and
any rows that already exist are left completely alone. Turning it back on
returns the feature exactly as it was — no migration, no backfill.

## The switches (`modules.config.ts`)

```ts
export const MODULE_CONFIG = {
  projects: false,
  salesOrders: false,
  finance: false,
  forecast: false,
  audit: false,
  advancedRoles: false,
  documentation: true,
} as const
```

This file is intentionally **pure** — no imports, no side effects — so it can
be safely imported from client components, server components, server actions,
framework-free services, and the DB seed scripts alike. The MVP release ships
with all four business plugins off; only the core CRM plus `documentation`
(this docs site) is enabled by default.

## The registry (`lib/modules.ts`)

`lib/modules.ts` is the single source of truth for plugin metadata and the
dependency graph:

```ts
export type ModuleId = keyof typeof MODULE_CONFIG

export type ModuleMeta = {
  id: ModuleId
  label: string
  dependsOn: ModuleId[]
}

export const MODULES: Record<ModuleId, ModuleMeta> = {
  projects: { id: "projects", label: "Projects", dependsOn: [] },
  salesOrders: { id: "salesOrders", label: "Sales Orders", dependsOn: ["projects"] },
  finance: { id: "finance", label: "Billing & Purchasing", dependsOn: ["projects", "salesOrders"] },
  forecast: { id: "forecast", label: "Forecast", dependsOn: [] },
  audit: { id: "audit", label: "Audit log", dependsOn: [] },
  advancedRoles: { id: "advancedRoles", label: "Advanced roles", dependsOn: [] },
  documentation: { id: "documentation", label: "Documentation", dependsOn: [] },
}
```

`ModuleId` is derived automatically from `MODULE_CONFIG`'s keys — adding a new
key to the config is the only type-level wiring needed. Three pure functions
gate everything else:

| Function | Used for |
|---|---|
| `isModuleEnabled(id)` | Synchronous check — nav filtering, conditional rendering, dynamic-import guards. |
| `assertModuleEnabled(id)` | Throws `"The <Label> module is disabled."` — first line of a module's non-`withModule` server actions. |
| `validateModuleConfig()` | Boot-time check (called from `instrumentation.ts`): every enabled module's dependencies must also be enabled, or the process **refuses to start**, naming exactly what's wrong. |

## The dependency graph

The graph is **code, not config** — an operator cannot express an invalid
combination through `modules.config.ts` alone, because the boot check catches
it:

```
salesOrders → projects
finance      → projects, salesOrders
(projects, forecast, audit, documentation have no dependencies)
```

`finance` roots its document chain on an approved sales order that itself
hangs off a project, so it depends on both `projects` and `salesOrders`
transitively as well as directly. Enabling `finance` without both makes the
app refuse to boot.

## The 7 modules

| id | Label | What it does | Depends on |
|---|---|---|---|
| `projects` | Projects | Delivery projects (Release 3). *Payment Milestones* is a **core** feature and is not gated by this flag — it lives directly under a Funnel with no Project dependency. | — |
| `salesOrders` | Sales Orders | Accepted-quote → sales order, per-tenant numbering, approval workflow (Release 2). | `projects` |
| `finance` | Billing & Purchasing | Billing + purchasing (order-to-cash / procure-to-pay finance documents) and intercompany billing (Release 6). | `projects`, `salesOrders` |
| `forecast` | Forecast | Probability-weighted billing forecast and executive reporting (Release 4) — a report-only Postgres view over existing data. | — |
| `audit` | Audit log | The audit-trail **viewer** surface. The underlying log is always recorded regardless of this flag; disabling only hides the `/audit` reporting UI. | — |
| `advancedRoles` | Advanced roles | Custom roles, the granular per-module permission-matrix editor, and seniority-tier editing. Off = fixed preset roles + basic role assignment + a simple reporting line — the permission **engine** itself always runs. | — |
| `documentation` | Documentation | This in-app documentation site. On by default. | — |

## The 6 moving parts

| File | Role |
|---|---|
| `modules.config.ts` | The switches — one boolean per plugin. |
| `lib/modules.ts` | The registry — `ModuleId`, `MODULES` metadata + dependency graph, `isModuleEnabled` / `assertModuleEnabled` / `validateModuleConfig`. |
| `lib/module-guard.ts` | Route guard — `requireModule(id)` calls `redirect("/dashboard")` when a plugin is off. `server-only`; kept tiny so a page doesn't transitively pull in the full `db` graph just to gate itself. |
| `lib/actions.ts` | Action guard — `withModule(id, permission, fn)` = `assertModuleEnabled(id)` then the normal tenant/RLS-scoped `withTenant(permission, fn)`. See [API Reference](/api-reference) for the full pattern. |
| `instrumentation.ts` | Boot check — runs `validateModuleConfig()` on startup in every environment (not just production) and refuses to boot on an inconsistent config. |
| Nav + permissions | `components/app-sidebar.tsx` and `components/command-palette.tsx` tag items with an optional `module?: ModuleId`; `lib/permissions.ts` tags each roles-matrix group the same way. All are filtered through `isModuleEnabled`. |

## Operator: enabling or disabling an existing module

1. Edit `modules.config.ts` — flip the flag (and any dependency it needs; the
   boot check validates this).
2. Rebuild and redeploy (`pnpm run build` + restart, or `docker compose up -d
   --build`). There is no per-tenant flag and no CLI — the config file is the
   single source of truth for the whole deployment.
3. Nothing else. No migration, no data change. Re-enabling shows all retained
   data exactly as it was left; disabling only hides access to it.

Want to build a new one instead? See [Modules → Contributing](/modules/contributing)
for the full technical recipe and the five invariants that keep this system safe.
