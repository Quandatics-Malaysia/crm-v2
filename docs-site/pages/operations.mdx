This page describes the production operator model for the new client-hosted architecture: vendor control plane in Cloudflare and source-free signed runtime on client infrastructure.

## Environments

- **Production**: `app.quandatics.com` with client data and active signed deployment
- **Staging**: isolated preview environment and dry-run deployment stack (`staging.app.quandatics.com` by default)
- **Cloud control plane**: Cloudflare Workers/D1/R2 that stores licenses, entitlements, and deployment state

## Control and deployment model

The operator flow is now:

1. Internal build pipeline creates immutable images (app, migrator, backup, deployment agent).
2. Images are signed and published to a private registry.
3. Vendor operators issue an entitlement envelope (modules, seats, status).
4. Clients pull only signatures and image digests, never source code.
5. Agent verifies signature + entitlement proof before applying runtime changes.
6. Health checks confirm rollout success; failed releases are rolled back to the last known-good signed bundle.

## What changed from older flow

- No server-side build.
- No source code deployment to client hosts.
- No long-lived source checkout on live hosts.
- No “self-serve” upgrade path for licenses or seats.
- No direct control-plane bypass from the client app.

## Minimum governance rules

- Client users can see health/version and operational status, but cannot access signing keys, tokens, or control-plane secrets.
- Vendors retain license creation, seat limit changes, module activation/disable, and production deployment controls.
- Any production change is logged with deployment identity and immutable digests.

## If something fails

- Recheck deployment manifest verification and backup evidence in the control plane.
- Validate the entitlement status of the target organization.
- Perform fallback to previous deployment digest before touching client data.
