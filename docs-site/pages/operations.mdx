How the Quandatics CRM is built and deployed, at a glance. The full operator
runbook — server access, backups & restore, database admin, and hardening —
lives in **`OPERATIONS.md` in the repository** (kept out of this public site on
purpose).

## Environments

- **Production** — the live app, deployed from a signed SemVer release after approval.
- **Staging** — an isolated stack built from the `staging` branch, so changes
  can be reviewed before they reach production. Its Cloudflare quick-tunnel URL
  changes on each redeploy and is published in the latest workflow summary.

The flow is: **feature branch → `staging` → `main` → signed release → production approval**.

## How a deploy works

Every release follows the same gate:

1. A **quality gate** runs on a GitHub-hosted runner — lint, typecheck, tests,
   and a production build. A pull request must pass it before merge.
2. Vendor CI builds four immutable images, scans them, emits SBOM evidence, and
   signs each digest with GitHub OIDC and Cosign.
3. The protected production workflow downloads only the source-free client
   bundle, verifies vendor signatures, migrates, checks health, and rolls back
   if a required gate fails. Production never builds application source.

Staging remains an isolated source build from its own branch and temporary URL.

## Modules

Optional features (Projects, Sales Orders, Finance, Forecast, …) are toggled by
a single boolean each in `modules.config.ts` and take effect on the next
rebuild. See **[Modules](/extensibility/plugin-system)** for the full plugin system.

## Where the details live

For anything operational — connecting to the database, running migrations,
backups and restore, or hardening — read `OPERATIONS.md` in the repository. It is
intentionally not published here.
