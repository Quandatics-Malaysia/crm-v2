# Incident response

Follow this sequence for production incidents in the signed deployment model.

## 1) App unhealthy

1. Confirm release channel and digest in system status.
2. Check most recent deployment status and health output.
3. If checks are failing after rollout, rollback to previous manifest.
4. Validate PostgreSQL and storage volumes remain mounted and writable.
5. Re-run health until stable before resuming.

## 2) Entitlement mismatch

1. Confirm tenant status in the control plane (`active` / `suspended` / `disabled`).
2. Confirm module list matches licensed plan.
3. If suspended, verify read-only behavior is active.
4. Reactivate through control plane only after issue resolution.

## 3) Backup / restore issue

1. Rebuild backup artifact from current running runtime.
2. Compare backup metadata with deployment identity.
3. Validate signed backup proof before trying restore.
4. Keep last successful production runtime available for emergency fallback.

## 4) Deployment blocked by verification

1. Verify manifest digest exists and is correct.
2. Confirm image signatures are present and trust chain is valid.
3. Ensure deployment env contains required runtime file inputs.
4. Retry from known-good manifest; do not change policy from client host.

## 5) Module or seat control complaint

1. Verify the tenant’s status and seat count from vendor control plane.
2. Confirm no local user edits can override module gates.
3. If needed, temporarily suspend or disable tenant from control plane.

## Communications

- Record a brief timeline in the incident note:
  - started at
  - trigger
  - rollback/repair action
  - final status
- Attach deployment manifest IDs and health timestamps.

## Escalation rule

- If two consecutive rollbacks are required in one day, stop further deployments
  until release root cause is reviewed.
