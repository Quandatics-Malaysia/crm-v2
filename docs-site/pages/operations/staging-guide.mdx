# Staging guide

Use staging for acceptance checks before promotion to production.

## What staging validates

- Container image verification
- Migrator execution path
- Entitlement transitions (active / suspended / disabled)
- Module visibility and write protection
- Backup proof and lock-state behavior
- Rollback/recovery readiness

## Recommended topology

- Separate compose project name from production
- Isolated PostgreSQL volume and storage location
- Separate `CONTROL_PLANE_URL` and deployment identity token
- Read-only access to customer production credentials

## Setup checklist

1. Provision a dedicated staging host entry, for example `staging.app.quandatics.com`.
2. Point it to an isolated runtime stack and database.
3. Use only release artifacts from the signed registry.
4. Keep staging identity separate from production in the control plane.
5. Create and register a staging client in the control plane for acceptance testing.

## Staging deployment sequence

1. Merge changes behind normal branch checks.
2. CI publishes signed release candidates.
3. Staging agent pulls candidate images.
4. Deployment is applied and health checks run.
5. Vendor team validates UI and operational behavior.
6. Candidate remains isolated until marked accepted.

## Data strategy

- Keep staging data synthetic when possible.
- Never use real production customer backups in staging unless approved and scrubbed.
- Do not mix production identity with staging deployment identity.

## Acceptance criteria before promotion

- Health endpoint passes.
- License state behaves correctly for all tested tenants.
- Module gating and read-only constraints match policy.
- Backup/restore test pass with signed proof.
- No unauthorized source code artifacts remain in runtime images.

If staging fails, production is unchanged.
